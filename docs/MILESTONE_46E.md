# Milestone 46E — Explicit Second-Basis Epoch Fresh Re-entry Verification

Decision: D232

## Product question

46D / D231 explicitly adopts one exact second-root-backed governed session in-process.
That adoption intentionally does not establish fresh-process second-epoch restartability.

37A / D190 already owns the exact typed model needed to reconstruct one second evidence-basis epoch above a persisted 35D/35E first-root continuation. 37B / D191 separately owns durable locator-overlay persistence.

46E asks only:

> Can the exact historical 46D adopted session be freshly reconstructed through existing 37A from caller-explicit current locators, while leaving the mounted governed state and immutable launch provenance unchanged and without writing a 37B overlay?

## Decision

Add one concrete product verification boundary:

```text
exact 46D adoption
+ explicit prior 35D/35E continuation overlay
+ explicit appended-member locators
+ explicit second changed working-set/note/transition/root/edge/declaration locators
→ existing 37A plan
→ public 37A fresh reconstruction
→ bounded two-layer identity comparison
→ locked verification receipt
```

while:

```text
46E verification
!= 37B persistence
!= controller promotion
!= launch-provenance mutation
!= global branch/head authority
```

## Prior art and reuse

Internal prior art is decisive:

- 44F / D223 proves the product separation between adopted state and fresh-process verification;
- 37A / D190 owns second-basis typed re-entry and two-layer fresh reconstruction;
- 37B / D191 owns later proof-gated durable overlay persistence;
- 46D / D231 supplies the exact historical second-basis adoption target;
- 45A / D226 separates immutable launch provenance from mutable current governed state.

No new re-entry plan type, persistence format, inspection schema, or generic repeated-epoch abstraction is introduced.

Conclusion: **no end-to-end substitute demonstrated in this review**.

## Exact authority subject

The 46E application helper requires exactly:

`ChromiumResearchSecondChangedBasisSessionAdoptionResult`

The retained prior first-root continuation is reached through the exact 46D product chain:

```text
adoption
→ 46C edge
→ 46B root
→ 46A transition
→ exact retained ChromiumResearchRootBackedSessionContinuationReentryResult
```

No separate caller-supplied in-memory prior controller is accepted as authority.

## Explicit locator discipline

46E requires every durable location explicitly for the current operation:

1. prior 35D/35E continuation overlay;
2. one locator set per appended changed-basis member;
3. changed working-set source;
4. changed working-set-note source;
5. second 33B transition source;
6. second 34A root source;
7. first post-second-root 34B edge source; and
8. second-root-backed declaration source.

All Textual path inputs begin blank.

No value is copied or inferred from 46A–46D persistence receipts, persisted launch provenance, raw 36D handoff context, checkpoint destinations, directories, filenames, or displayed hashes.

A persisted 35D/35E launch location remains provenance/display context only. A raw 36D launch remains pathless. A raw launch may verify 46E only when the researcher explicitly supplies a valid persisted continuation overlay whose fresh reconstruction proves the same durable prior ancestry; that supplied path is not backfilled into launch provenance.

## Two-layer verification

Public 37A first freshly reconstructs the explicit prior continuation and then the second changed-basis epoch.

46E compares that fresh result against the exact historical 46D lineage.

### Prior first-root layer

Required equality:

- governed prior-continuation presentation;
- terminal prior-continuation edge SHA-256;
- retained first 34A root SHA-256.

Fresh Python objects and path equality are not required.

### Second-root layer

Required equality:

- second 34A root SHA-256;
- second-root-backed declaration SHA-256;
- first post-second-root endpoint SHA-256;
- governed adopted presentation.

These are bounded integrity/coherence relationships only. They do not authenticate sources, establish chronology, or prove semantic support.

## Product surface

The dedicated `SecondChangedBasisEpochReentryResearchSessionShell` subclasses the 46D adoption shell.

The 46E form mounts only after one exact successful 46D adoption and retains that adoption as its historical proof target.

The form renders member-specific locator fields using the established supported member families:

- paragraph note: capture + note;
- exact-range note: capture + note;
- comparison note: first capture + second capture + note.

Successful verification locks the form and retains one exact `ChromiumResearchSecondChangedBasisEpochReentryResult`.

The fresh 37A controller remains proof evidence only. The shell snapshots and requires unchanged:

- mounted `research_controller`;
- mounted `research_session`;
- `research_reentry`;
- retained historical first-root continuation re-entry.

A later ordinary rollover after 46D therefore does not retarget the 46E proof subject.

## Inspection behavior

Inspectable persisted 35D/35E and raw 36D product shells inherit the 46E surface.

46E requires no new inspection projection because successful verification does not change mounted governed state.

For both launch families:

- the exact immutable `launch_provenance` object remains unchanged;
- `current_state` remains unchanged by verification;
- raw 36D launch provenance remains pathless even when an explicit persisted prior overlay is used as one 46E input.

## Textual dispatch rule

The 46E shell handles only its own verification button and deliberately does not call `super().on_button_pressed(event)` for unhandled buttons.

Textual dispatches inherited handlers through the MRO. Manual parent dispatch would schedule inherited actions twice, reproducing the defect exposed during 46D CI.

## Falsifiability

Focused tests require:

- exact 46D result type;
- public 37A reconstruction of both ancestry layers;
- rejection of a wrong prior overlay or wrong second-root locator;
- a freshly created controller distinct from the mounted controller but presenting the exact 46D governed session;
- no 46E controls before successful 46D;
- every 46E locator input blank when mounted;
- no 37B overlay destination or persistence action;
- successful proof leaves mounted governed state unchanged;
- successful raw-36D proof leaves launch provenance object-identical and pathless.

Repository Zero remains the full-suite gate on Python 3.11–3.14.

## Non-goals

46E adds no 37B persistence, automatic relaunch, second-epoch checkpoint, third/fourth basis change, arbitrary-depth ancestry, generic Nth-epoch helper, locator discovery/prefill, launch-path backfill, CLI flag, browser reacquisition, global current/latest/head/chronology authority, path identity, authorship/authenticity/trusted-time authority, semantic-support/citation authority, or autonomous research behavior.

## Earned statement

A successful 46E establishes only:

> From one exact historical 46D adopted second-basis session and caller-explicit current durable locators, Pyxis can use the existing 37A boundary to freshly re-enter the same two-layer first-root/second-root ancestry and governed session, retain that fresh result as visible proof, and leave the mounted session and immutable launch provenance unchanged without writing durable 37B restart configuration or granting global branch, chronology, or semantic authority.
