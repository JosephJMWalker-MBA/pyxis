# D206 — Third-epoch shell launch lineage must be freshly proven from explicit persisted location

A third-epoch product surface must not treat an arbitrary caller-owned re-entry object plus a filesystem path as launch authority.

Before CLI, Textual, or another product surface may carry a persisted third-basis-epoch session, Pyxis must bind one explicitly supplied 40B or 40C/40D overlay location to the fresh typed re-entry reconstructed from that exact location and prove that reconstruction matches the already-earned lineage.

For a 40B third-epoch overlay, the proof must match retained second-epoch continuation presentation and endpoint, retained first-root identity, retained second-root identity, third-root identity, third-epoch presentation, and third-epoch endpoint.

For a 40C/40D continuation overlay, the proof must additionally match the current continuation presentation and endpoint before applying the complete nested three-root ancestry proof.

The resulting frozen launch-lineage record may carry only:

- the explicit resolved overlay location as operational location context; and
- the fresh re-entry reconstructed from that location during proof.

The wrapper does not make path identity, Python object identity, chronology, branch state, or latest/current/head selection authoritative. Path-distinct overlays are acceptable only when explicit fresh reconstruction proves equivalent durable governed state and ancestry.

40D cumulative continuation uses the existing 40C overlay/re-entry family, so it does not receive a separate launch-lineage type.

This application-layer proof is a prerequisite for later third-epoch CLI/Textual launch or three-root authority inspection. D206 adds no UI, CLI behavior, persistence format, discovery, new basis epoch, generic `epoch[n]` representation, arbitrary-depth ancestry, authorship/authenticity/trusted-time claim, semantic-support claim, or citation authority.
