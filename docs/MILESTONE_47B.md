# Milestone 47B — explicit third changed-basis revision root

Decision: D236.

## Boundary

47A made one exact third public-33B changed-basis transition a concrete product result above an actively governed second-basis-epoch continuation.

47B adds only the next authority boundary:

```text
exact successful ChromiumResearchThirdChangedBasisTransitionResult
+ explicit new human revised rationale
+ explicit current prior endpoint edge path
+ explicit current changed working-set path
+ explicit current changed working-set-note path
+ explicit current third-transition path
+ explicit no-overwrite third-root destination
→ public 34A third revision root
→ public 34A persistence
→ fresh public 34A relink
```

while:

```text
47B root
!= first post-third-root 34B edge
!= third-epoch declaration/session
!= 40A fresh re-entry
!= 40B restart overlay
!= adoption
!= current/latest/head authority
!= generic Nth-root abstraction
```

## Why this is a product seam

The existing lower-level third-epoch machinery reconstructs authority only after durable third-transition/root/edge/declaration artifacts already exist. It therefore cannot substitute for the user-visible operation that gives the exact 47A transition its first human-authored 34A root.

46B / D229 is the exact prior product analogue for the second changed-basis root. Public 34A already owns the generic record semantics, persistence, fresh relink, exact-different-rationale rule, and no-overwrite behavior. 47B reuses those boundaries rather than reimplementing them.

Conclusion from the prior-art review: **no end-to-end substitute demonstrated in this review**.

## Exact authority subject

The application helper requires exactly:

`ChromiumResearchThirdChangedBasisTransitionResult`.

Structural similarity is not an alternative product authority family. The result retains the exact supplied 47A object by identity.

The retained loaded transition must continue to match the transition receipt and the exact prepared third working-set/note identities already earned by 47A.

## Explicit locator discipline

The root form starts with:

- one blank human revised-rationale field;
- five blank durable path fields.

The durable paths are:

1. prior endpoint edge source;
2. changed working-set source;
3. changed working-set-note source;
4. third changed-basis transition source;
5. no-overwrite third-root destination.

47B does not prefill those fields from 47A receipts, launch provenance, directories, filenames, hashes, checkpoint paths, or any inferred current/latest/head location.

Receipts prove earlier successful operations. They do not become perpetual location authority.

## Public 34A ownership

47B delegates root creation to:

`create_chromium_research_session_working_set_transition_revision_root(...)`

persistence to:

`persist_chromium_research_session_working_set_transition_revision_root(...)`

and fresh relink to:

`load_chromium_research_session_working_set_transition_revision_root(...)`.

The application adapter adds only bounded product coherence checks:

- the exact 47A loaded transition matches its persisted transition SHA;
- prior endpoint identity matches the exact 47A controller endpoint;
- successor working-set identity matches the exact 47A preparation;
- successor note identity matches the exact 47A preparation;
- public persistence retains the exact in-memory root;
- fresh root SHA matches persistence;
- fresh transition SHA matches the exact 47A transition;
- fresh human revised wording matches the explicit supplied text.

## Historical authority

Once 47A has successfully persisted its third changed-basis transition, that transition is durable historical relationship authority.

A later rollover of the older mounted second-epoch branch does not retarget or invalidate the transition for 47B. The historical transition can still receive its explicit root afterward.

This coexistence is not a branch-preference claim. It does not make either branch current/latest/head by global inference.

During root persistence, 47B snapshots the currently mounted controller, session, and current typed second-epoch continuation and proves they remain object-identical afterward.

## Product surface

47B is a dedicated product layer over the four 47A products:

- persisted second-epoch continuation launch;
- pathless second-epoch continuation handoff;
- inspectable persisted launch;
- inspectable pathless handoff.

The plain 47A product does not gain 47B implicitly.

Successful 47A persistence mounts exactly one root form. Root failure is retryable. Root success locks that exact form.

No third-root-edge or third-epoch adoption controls are mounted by 47B.

## Launch provenance

47B does not mutate launch provenance.

For persisted 37C/37D launch families:

- the existing launch provenance object remains exact;
- its launch location context remains unchanged.

For raw/pathless continuation handoff:

- the launch provenance object remains exact;
- launch location context remains `None`.

Root persistence also does not mutate inspection current state unless some separate governed operation actually changes mounted state.

## Textual event ownership

The 47B product mixin handles only:

`persist-research-third-changed-basis-revision-root`.

It does not manually call the inherited `on_button_pressed` handler. Inherited 47A/second-epoch Textual handlers remain MRO-dispatched. This avoids duplicate inherited action scheduling.

The 47B application method may call the inherited 47A persistence method directly because that is an explicit application workflow boundary, not Textual event redispatch.
